## 1단계: 난이도 판정 + 계획 (직접 수행)

**난이도 등급** (영향 범위 기준 — 둘 이상에 걸치면 높은 쪽):

| 등급 | 기준 | 구현 | 검수 |
|---|---|---|---|
| **S 단순** | 파일 1~3개, 위치·내용이 정해짐, 로직 변경 없음(문구·주석·상수 한 곳·체크박스) | `fixer`(Haiku) 또는 메인이 직접 | 메인이 diff 직접 확인 + tsc·lint |
| **M 일반** | UI 컴포넌트·패널·훅 분리, 독립 모듈, 검증 스크립트, 문서 | `coder-sonnet`(Sonnet) | `reviewer` 를 `model: opus` 로 호출 |
| **C 핵심** | `utils/slice-*`·`workers/`·`utils/task0/`·`utils/gcode/`·`components/BabylonScene.tsx`·`components/babylon/`·`data/`·`support/`·`utils/dental/`·`types/printer.ts` 기본값·좌표계·산출물 바이트 | 메인(Opus)이 직접 또는 `coder`(Opus) — worktree 격리·병렬이 필요할 때 | `reviewer`(Fable 기본) |
| **A 설계 필요** | 구조 경계(handle·repo·워커 메시지·스키마) 변경, 알고리즘(마진·서포트·커버리지·좌표·노광), 규격 해석이 갈리는 것, 담당자(유승제·지현규) 리뷰 대상 | 먼저 `architect`(Fable) 에게 결정·계획 골격을 받고 → C 로 진행 | `reviewer`(Fable) |

- **검수는 반드시 구현한 모델과 다른 모델**로. Sonnet 구현 → Opus 또는 Fable 검수, Opus 구현 → Fable 검수. 메인(Opus)이 직접 구현했으면 Fable 검수.
- 핵심 로직은 Haiku·Sonnet 에게 맡기지 않는다. 단순 작업에 Fable·Opus 를 쓰지 않는다. 품질이 비용보다 우선 — 등급이 애매하면 높은 쪽.

**계획** 작성:
1. (A 등급이면) `architect` 에게 문제·제약·이미 배제한 선택지를 주고 결정·구현 계획 골격·수용 기준 초안을 받는다. 결과를 그대로 믿지 말고 규칙·규격과 대조한 뒤 채택.
2. 다음을 포함한 구현 계획 작성:
   - 수정 파일 목록 + 의존성 순서 + **파일별 담당 에이전트**(C 파일은 coder/메인, M 파일은 coder-sonnet, S 는 fixer)
   - 각 파일의 구체적 변경 내용
   - **수용 기준**: 완료 판정에 쓸 구체적·검증 가능한 조건 목록 (산출물 바이트 보존 여부, 새 검증 스크립트·대조군 포함)
3. 로드맵·데모 계획·규격서와 충돌하거나 범위가 모호하면 **코딩 전에 사용자에게 확인**. 불확실한 것은 추측으로 메우지 않는다.
4. 브랜치: `origin/integrate/v2-mainline` 에서 `feat/<이름>` (문서만이면 `docs/<주제>-<날짜>`). 다른 열린 PR 이 같은 문서 줄을 고치면 그 PR 브랜치 위에 쌓는다(WORKFLOW §8).

## 2단계: 구현

등급에 맞는 에이전트에게 계획 전체(파일 목록, 변경 내용, 수용 기준)를 전달합니다. 계획을 요약하지 말고 그대로 전달하세요. 함께 전달할 것:
- 작업 브랜치/worktree 와 기준 커밋 — "시작 시 `origin/integrate/v2-mainline` 기준인지 확인, 아니면 reset"
- 완료 전 검증 명령(`npx tsc --noEmit` / `npm run lint` / `npx tsx scripts/verify-*.mjs` 전부 exit 0 / `npm run build`)과 기준선(CLAUDE.md "알려진 이슈" 절)
- 서로 독립인 파일 묶음(예: UI 는 coder-sonnet, 워커는 coder)만 **병렬**로. 같은 파일을 두 에이전트가 고치지 않는다.
- coder-sonnet·fixer 가 "핵심 영역 — 멈춤" 으로 보고하면 그 부분은 coder/메인이 이어받는다.

## 3단계: 검수

`reviewer` 에게 작업 목표 + 수용 기준 + 검토 대상(브랜치·worktree) + **구현한 에이전트와 등급**을 전달하여 diff 를 검토시킵니다.
M 등급이면 호출 시 `model: opus`, C·A 등급이면 기본(Fable). reviewer 는 자동 검증을 직접 재실행합니다.
S 등급은 메인이 `git diff` 를 직접 읽고 tsc·lint 를 돌려 판정합니다.

## 4단계: 판정 및 분기

reviewer의 결과를 그대로 수용하지 말고 직접 타당성을 판단한 뒤:

- **FAIL이 타당하면**: 문제 목록과 수정 지시를 구현한 에이전트에게 전달하여 재작업 → 3단계로.
  재작업은 최대 3회. 그래도 FAIL이면 중단하고 현재 상태·문제·선택지를 사용자에게 보고.
  검증이 실패했는데 성공으로 보고하지 않는다.
- **PASS이면**:
  1. 커밋(`feat:`/`fix:`/`docs:`/`chore:` + 한국어 요약) → push → **PR 생성** (대상 `integrate/v2-mainline`).
     PR 본문: 무엇을/왜, 수정 파일, **에이전트·모델별 담당**, AI 검수 이력(FAIL→수정 포함), 자동 검증 실측, 산출물 바이트 변화 여부,
     **"조우현 확인 포인트"**(`docs/WORKFLOW.md` §4-2 에서 해당 항목을 골라 "무엇을 누르면 무엇이 보여야 정상인지")
  2. `docs/통합로드맵.md` 해당 체크박스 갱신을 같은 PR 에 포함
  3. 사용자에게 한국어로 결과 요약(변경 파일·구현 내용·테스트 결과·남은 문제) + PR 링크 + 확인 포인트 안내. 작업일지는 세션 마감 때 `/worklog`
  4. 머지는 조우현이 한다. 머지 후 브랜치·worktree 삭제(WORKFLOW §8 — node_modules 정션 먼저 제거)
