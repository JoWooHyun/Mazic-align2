# MazicAlign 팀 개발 워크플로우

팀원 3명 + AI(Claude Code)가 같은 흐름으로 개발하기 위한 문서.
모든 작업(사람이 직접 하든, AI에게 시키든)은 이 흐름을 따른다.

## 1. 역할 분담

### 사람

| 역할 | 담당 |
|---|---|
| 프로젝트 리드 (조우현) | 개발계획서 작성, 작업 배분, 최종 머지 승인 + 슬라이서 코어·FDM G-code (2노즐 하이브리드 대비) |
| 유승제 | v2 인프라 전반 + 서포트 **구조물** (기둥/브릿지 생성·편집·CSG) — `docs/개발방향_v2서포트_유승제.md` |
| 지현규 | 서포트 **배치 판단** (마진·브러쉬·오버행·아일랜드 검출) + dental 특화 도구 — `docs/개발방향_슬라이서프론트_지현규.md` |

※ 서포트 역할 경계 (2026-07-07 결정): 지현규의 검출 결과(마진 라인, island faces)가 유승제의 서포트 생성 입력이 되는
상호보완 구조로 통합한다. 아키텍처 결정 전문은 `docs/아키텍처결정_20260707.md`, 이식 계획은 `docs/통합로드맵.md` 참고.

### AI (Claude Code)

| 역할 | 모델 | 하는 일 |
|---|---|---|
| **플래너/검수자** | Fable (메인 세션) | 작업 계획 수립, 코드 리뷰, 재작업 지시, 적용 판단 |
| **코더** | Opus (`coder` 서브에이전트) | 계획서에 따른 실제 코드 작성 |
| **리뷰어** | 세션 모델 상속 (`reviewer` 서브에이전트) | 구현 결과를 수용 기준 대비 독립 검토 |

## 2. 작업 단위와 흐름

모든 기능 작업은 다음 단위로 흐른다:

```
통합로드맵 Step (또는 GitHub 이슈)
   → feat/<기능명> 브랜치 (기준: integrate/v2-mainline)
   → 구현 (사람 직접 또는 /dev-cycle)
   → 수동 검증 (아래 체크리스트)
   → PR (조우현 확인 포인트 포함) → 조우현 머지
   → 로드맵 체크박스·작업일지 갱신
```

## 3. AI 개발 사이클 (/dev-cycle)

Claude Code에서 `/dev-cycle <작업 내용>` 실행 시 다음 루프가 돈다:

```
[1] 계획 (Fable)
    - CLAUDE.md, 개발계획서, 관련 코드 파악
    - 수정 파일 목록 + 의존성 순서 + 수용 기준(acceptance criteria) 작성
         ↓
[2] 구현 (Opus coder 에이전트)
    - 계획과 수용 기준을 그대로 전달받아 코드 작성
         ↓
[3] 검수 (reviewer 에이전트 → Fable 판단)
    - diff를 수용 기준·수정 규칙 대비 검토
    - 판정: PASS / FAIL(사유 + 수정 지시)
         ↓
[4] 분기
    - FAIL → 수정 지시를 coder에게 전달, [2]로 (최대 3회)
    - PASS → PR 생성 + 본문에 "조우현 확인 포인트" 작성
              → 조우현이 확인 후 머지 (= 최종 승인)
```

- 3회 반복 후에도 FAIL이면 중단하고 사람에게 판단을 넘긴다.
- 계획 단계에서 개발계획서와 충돌이 발견되면 코딩 전에 사람에게 확인한다.

## 4. 수동 검증 체크리스트 (v2 기준, 2026-07-08 개정)

자동 테스트가 없으므로 PR 전 `start-dev.bat`(또는 `npm run dev`) → `localhost:5173/v2`에서 확인:

1. **파일**: 프로젝트 생성 → "내 PC에서 열기"/드래그앤드롭으로 STL 로드 (백엔드 없이) → 새로고침 후 유지(IndexedDB)
2. **편집**: Select/Support/Dental 모드 전환 — 각 모드에서 기즈모·픽킹이 문서대로 동작
3. **서포트(유승제)**: 자동 생성 → 기둥/브릿지 편집 → STL 회전 시 즉시 추종, undo(Ctrl+Z)
4. **Dental(지현규)**: 브러쉬 색칠(주황) → 마진 찾기(초록 라인, 회전 추종) → 마진 안 더블클릭 채움 → 아일랜드 검출(마젠타)
5. **슬라이스 프리뷰**: 사이드패널 레이어 스크럽, 부피/무게/예상 시간 표시
6. **내보내기**: 마스크 ZIP(진행률 표시 + **내보내는 중 3D 뷰 조작이 끊기지 않아야 함**), CTB, G-code, STL
7. **프로파일**: 노광·리프트 값 수정 저장 → 예상 시간 즉시 갱신 → 내보낸 파일에 반영
8. `npm run lint` — 새 경고 0 (기존 40건 제외), `npm run build` 성공

작업이 건드린 영역의 항목은 필수, 나머지는 샘플링. 슬라이스/출력 계열 수정 시 5~7 필수.
dental 계열 수정 시 실모델(STL Sample 6개 — 이민정/홍연제) 회귀는 지현규 육안이 기준.

## 5. PR 규칙 (2026-07-08 개정 — 최종 승인·머지 = 조우현)

- **최종 검토·머지는 리드(조우현)가 한다.** AI가 만든 PR은 GitHub 규칙상 조우현이 Approve 버튼을
  누를 수 없으므로(본인 계정 authored), **머지 버튼 = 승인 행위**로 간주한다.
- PR 본문 필수 항목: 무엇을/왜, 수정 파일, AI 검수 이력(FAIL→수정 포함), 그리고
  **"조우현 확인 포인트"** — 비개발자가 실행해서 판단할 수 있는 체크리스트 (뭘 눌러보고 뭐가 보이면 OK).
- 유승제·지현규 리뷰는 **필수가 아닌 선택** — 본인 담당 영역의 설계가 크게 바뀌는 변경
  (예: BabylonScene 구조, 마진 알고리즘, IndexedDB 스키마)일 때만 리드가 지정한다.
- 개발자가 직접 올린 PR은 기존대로: 조우현이 Approve + 머지.
- 슬라이서 코어/마진 잠금 영역 변경은 반드시 PR 본문에 명시.

## 6. 문서 갱신 의무

- 기능 완료 시: 작업일지(`MazicAlign_작업일지_*.txt`)에 날짜별 항목 추가
- 계획 변경 시: 개발계획서 갱신 후 팀 공유
- 코드 구조가 바뀌면: `CLAUDE.md`의 코드 구조 표 갱신
