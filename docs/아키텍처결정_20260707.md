## ADR-1. 메인라인: 유승제 v2 기반 (`integrate/v2-mainline`)

**결정**: 유승제의 v2 코드베이스(`features/v2/`)를 새 메인라인으로 삼는다.
단, **조우현 구현이 우세한 영역은 조우현 것을 채택**한다 (아래 판정표).

**근거**:
- v2가 인프라(프로젝트 관리, undo/redo, 프린터 프로파일, ctb 인코더, IndexedDB 계층)를 가장 많이 보유
- v1을 포함하고 있어 나머지 두 사람 작업을 이식으로 수용 가능
- 문서-코드 정합성 검증을 통과한 코드베이스

**슬라이서 A(조우현) vs B(유승제 v2) 기능별 판정** (2026-07-07 코드 분석):

## ADR-2. 데이터 계층: IndexedDB (Express/SQLite 백엔드 동결)

**결정**: IndexedDB(`features/v2/data/db.ts`, repo 패턴)를 표준 저장소로 한다.
Express/SQLite 백엔드는 **동결** — 삭제하지 않되, 신규 코드가 의존하는 것을 금지한다.

**근거** (리드 위임에 따른 AI 판단):
1. v2 메인라인이 이미 IndexedDB 위에 완성돼 있음 (supports/stl-files/projects repo + undo 연동)
2. 로컬 전용 앱이라 서버가 필수 요건이 아님 — 서버 없이 실행되면 설치/배포/시연이 단순해짐
3. **"나중에 바꾸더라도 괜찮은" 조건 충족**: v2의 데이터 접근이 전부 `data/*.repo.ts` 모듈로 격리돼 있어, 향후 서버 저장(협업/백업)이 필요해지면 repo 구현만 REST로 교체하면 됨. 반대 방향(SQLite→IndexedDB 재전환)보다 이 방향이 이식 비용이 낮음.
4. 백엔드를 지금 삭제하지 않는 이유: v1 페이지(히스토리/업로드)가 동결 기간 동안 참조하고, 지현규 v1 코드 이식이 끝날 때까지 안전망으로 유지.

**가역성**: repo 인터페이스 유지가 조건. repo 모듈을 우회한 직접 IndexedDB 접근은 금지 (리뷰 대상).

## ADR-3. 서포트 분담: 검출(지현규) → 생성(유승제) 파이프라인

**결정**: 두 구현 모두 유지하고 역할을 나눈다.
- **지현규 = 배치 판단**: 마진 찾기(잠금), 브러쉬 영역, 오버행/아일랜드 검출 — "어디에 서포트가 필요한가"
- **유승제 = 구조물 생성/편집**: trunk/브릿지 생성, manifold CSG, gizmo 편집, IndexedDB 저장 — "서포트를 어떻게 만드나"
- 연결 계약: 지현규의 검출 결과(마진 라인 points/edgeKeys, island faces, painted mask)를 유승제의
  서포트 생성 입력으로 전달하는 export API를 정의한다 (지현규 문서 4.7 구상 채택).

**근거**: 상호보완적 — 한쪽을 버리면 각각 "생성만 있고 판단 없음" / "판단만 있고 편집 없음"이 됨.
**제약**: 마진 알고리즘은 잠금 (`docs/references/feedback_margin_algorithm_lock.md`) — 이식 과정에서도 파라미터·로직 변경 금지, 변경 필요 시 지현규 컨펌.
