1. "얘는 왜 Y축이 Z축처럼 위아래로 올라가는지 모르겠다. 밑에 평면이 X,Z평면이 아니라 X,Y평면이면 될 것 같다."

## 2. B-12 — 회전 시 기즈모 축·POSITION 동반 이동

### 원인 A: 기즈모가 local 모드 — **v1에 있던 설정이 v2 이관 때 누락 (회귀)**

`features/v2` 전체에 `updateGizmoRotationToMatchAttachedMesh` **0건**.
Babylon 기본값이 **`true`(local 모드)** 라 그대로 적용된다. 라이브러리 타입 정의 원문:

> `If set the gizmo's rotation will be updated to match the attached mesh each frame (Default: true)`
> `Set the coordinate system to use. By default it's local.`

**구 v1은 명시적으로 껐다**:
- `frontend/src/utils/babylon.utils.ts:378` — `positionGizmo.updateGizmoRotationToMatchAttachedMesh = false;`
- `frontend/src/utils/babylon.utils.ts:384` — `rotationGizmo.updateGizmoRotationToMatchAttachedMesh = false;`

v2 `setup-gizmos.ts:19-21`은 기즈모 생성 후 `scaleRatio`만 설정 → **world 축 고정 설정이 이관에서 빠졌다.**

**⚠️ 이것만 고치면 안 된다 (증폭 요인)**:
`components/babylon/scene-actions.ts:24-26`의 `placePivotProxy`가 **프록시에 메시 회전을 복사**한다.
회전/스케일 기즈모는 이 프록시에 attach되므로(`scene-actions.ts:155-156`),
설정을 false로 해도 **프록시 자체가 기울어 링이 여전히 기울어 보인다. 두 곳을 함께 처리해야 한다.**
(`scene-actions.ts:14-15` 주석에 "회전은 모델 회전에 맞춰 로컬 축 링을 유지한다(현행 UX)" — 당시엔 의도된 동작이었으나 CHITUBOX 대조 결과 잘못된 방향)

### 원인 B: POSITION이 바뀌는 경로 — **회전축과 좌표 기준점의 불일치**

1. 드래그 시작 `setup-gizmos.ts:106-109`: `placePivotProxy(ctx, mesh)` → `mesh.setParent(proxy)`
   (setParent는 world 보존하며 **로컬 SRT 역산** → `mesh.position` 변경)
2. 드래그 중: 기즈모가 프록시를 회전, mesh는 자식이라 bbox 중심 축으로 함께 회전
3. 드래그 종료 `setup-gizmos.ts:188-194`: `mesh.setParent(null)` → 로컬 SRT 재계산
4. `utils/transform.ts:276-290` `readMeshTransform`이 **`mesh.position`(= origin)** 을 그대로 읽어 저장

**근본 원인**: `stl-loader.ts:118-137` `alignMeshToPlate`가 정점을 **바닥 중심**에 베이크 → **origin ≠ bbox 중심**.
그런데 B-9(PR #42)에서 **회전축만** bbox 중심으로 옮기고 **좌표 기준점은 origin에 남겨둬** 둘이 어긋났다.
→ bbox 중심 고정 회전이 origin을 중심 둘레로 **공전**시킨다.

**수치 검증 (리드 스크린샷)**: 공식 `pos' = Rd·(pos − p) + p` (`utils/transform.ts:114-131`에 구현됨)를
피벗 p에 대해 역산하면 **p = (y 34.4594, z −4.1950)** 이 유일해로 나오고, 이 값으로
회전 전 (0, 21, −1.196)에 X축 89°를 적용하면 **(0, 31.226, −17.600)** — **실측과 소수 3자리까지 일치**한다.
→ 공전 메커니즘이 수치로 확정됐다.

> ⚠️ **정정 (2026-08-13, B-12 구현 중 발견)**: 이 문서 초판에 적었던 "피벗 ≈ Y 26, Z −9"는
> 스크린샷 눈대중 근사치였고 실측값을 재현하지 못한다(그 값으로는 Y 18.11, Z −13.86이 나온다).
> **원인 규명(공식·메커니즘)은 옳았고 피벗 수치만 틀렸다.** 위 역산값이 정본이다.
> 재현 스크립트: `frontend/scripts/verify-transform-display.mjs` (c) 대조군.

**모델의 world 위치는 제자리**(setParent가 world 보존, `setup-gizmos.ts:98-99·169-170` 주석 명시).
그러나 **DB에 저장되는 값이 바뀌고 CHITUBOX와 동작이 다르므로 수정 대상이다.**
(초기 판단은 "표기 문제라 실질 무해"였으나 **CHITUBOX 캡처 ④로 뒤집혔다** — 정답지가 0을 유지한다.)

## 3. B-13 — 축 Z-up 표기

### 원인: Babylon 기본 Y-up을 **설계로 채택**한 것 (실수 아님)

- `useRightHandedSystem` 코드베이스 전체 **0건** → Babylon 기본 left-handed **Y-up**
- `utils/stl-loader.ts:51-53`: STL Z-up → Babylon Y-up을 **정점에 영구 베이크**
  ```ts
  mesh.rotation.x = -Math.PI / 2;
  mesh.bakeCurrentTransformIntoVertices();
  ```
- `utils/scene-setup.ts:43-47` CreateGround(XZ 평면), `:110-117` Y축=초록을 "위"로
- `pages/viewer/components/ViewportInfoPanels.tsx:49` `<span>Y (위)</span>`

※ 작업일지의 "Babylon STL 로더 Y/Z 스왑"은 **별건**이다. `slice-geometry.ts:44-60` — 로더가 정점을
`(x,z,y)`로 넣어 **감김(winding)이 뒤집히는** 문제이고 `normalizeTriangleWinding()`으로 이미 처리됐다(B-7).

### 영향 범위: **뷰어만이 아니다 — 슬라이서·CTB·G-code 코어 전부가 Y=높이 전제**

| 함수 | 위치 | 역할 |
|---|---|---|
| `sliceTrianglesAtY(triangles, y)` | `utils/slice-geometry.ts:117` | 슬라이서 **순수 코어** (`d0 = v0y - y`) |
| `sliceMeshAtY(mesh, y)` | `utils/slice-section.ts:67` | Babylon 래퍼 |
| 워커 | `workers/slice-batch.worker.ts:78` | 배치 슬라이스 |
| 서포트 검출 | `support/detect/layer-graph.ts:85` | 아일랜드/오버행 층 스캔 |
| G-code | `utils/gcode/fdm-gcode.ts:93` | FDM 경로 |

- `slice-geometry.ts:15-16`: "평면 Y = y 와 삼각형의 교차… 점은 world 좌표의 (X, Z)"
- `slice-rasterize.ts:22-25`: polygon = world (X,Z), `pixel_y = (D/2 − Z)/D × heightPx`

**Y=높이 전제 파일 규모**: 슬라이서/출력 ~15, 서포트 ~6, 씬/뷰어 ~12, dental(잠금 인접) ~4 → **약 35~40 파일**

### 판정: 내부 좌표계 변경은 **전면 개조 — 강력 비권장**

`sliceTrianglesAtY`→`AtZ`, 래스터 매핑, `matZupToYup()`(`support/assemble-core.ts:86`), 카메라 프리셋,
클립 플레인, 모든 낙하 레이(`Vector3(0,-1,0)`)를 동시에 뒤집어야 하고 **출력물이 직접 바뀐다.**
**margin-detect(잠금)** 도 Y 전제 위에 있어 잠금 영역을 건드리게 된다.

### 권장: 표시 레이어에서만 Z↔Y 스왑

**근거 — 이 코드베이스에 이미 같은 패턴이 있다**:
`utils/gcode/fdm-gcode.ts:12-13` — "Babylon (X,Z) → G-code (X,Y) / Babylon Y(높이) → G-code Z"
즉 **"내부 Y-up / 외부 Z-up"이 기존 규약**이다. 표시 레이어도 같은 방식이면 일관적이다.

바꿀 지점 (3~4 파일): `ViewportInfoPanels.tsx:44-54`(범례), `TransformPanel.tsx`(POSITION/ROTATION/SCALE),
`scene-setup.ts:110-121`(축 라인 색), `camera-views.ts`(프리셋 라벨)

**⚠️ 최대 리스크**: **Y↔Z 스왑은 반사(행렬식 −1)라 회전 부호가 뒤집힌다. 라벨만 교체하면 틀린다.**
회전 부호·짐벌 순서 검증이 필수이며, 이것이 B-12와 분리해서 진행하는 이유다.

> **✅ 해결 (2026-08-13, PR #45)**. 실제 구현에서 확정된 결론:
> - 매핑은 단순 스왑 `(x,z,y)`(det −1, 반사)가 **아니라** **`(x, −z, y)`(det +1, 순수 회전)** 를 쓴다.
>   det +1이라 회전 부호가 보존된다. 이 M은 실은 **Babylon X축 +90° 회전**과 같다.
> - **더 깊은 함정이 있었다**: 회전값을 **성분 교환**(`dispRY=−intRZ, dispRZ=intRY`)으로 환산하면
>   **복합 회전에서 틀린다.** 축 치환이 Babylon Euler 합성 순서(YXZ)와 교환되지 않기 때문.
>   예) 내부 (10,20,30) → 올바름 (18.199,−26.132,13.056) vs 성분교환 (10,−30,20).
>   올바른 해법은 **quaternion 켤레** `q_disp = qM·q_int·qM⁻¹`.
> - **가장 위험한 성질**: 성분 교환은 **단축 회전에서는 우연히 정확히 일치한다.**
>   단축으로만 테스트하면 결함을 그대로 통과시킨다 → 검증에 **복합 회전 케이스 필수**.
>   `verify-axis-display.mjs`의 대조군 ②가 이를 assert한다(단축 3/3 통과, 복합 4/4 불일치).
