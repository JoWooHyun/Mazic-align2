# 진단 — 재설계 서포트 점 과다 / 서포트 탭과의 차이

- 작성: 2026-08-24 (AI, 리드 실물 피드백 대응)
- 계기: 리드 v0.10.0 실물 테스트 — *"서포트 아직도 너무많다.. 서포트 탭에서의 서포트와 우리가 재설계한 서포트랑 왜이렇게 차이가 나는지 모르겠네."*
- 성격: **원인 규명까지만.** 수정은 별도 과제(아래 6장) — 검출 로직은 S-4b-2e 가 방금 검수 통과한 영역이라 즉흥 수정하지 않는다.

---

## 1. 결론 먼저

두 경로는 **애초에 다른 알고리즘**이고, 점 개수 차이의 주범은 하나다.

> **재설계 경로의 오버행 점 중복 제거가 "층 하나 안에서만" 돈다.**
> 그래서 수직으로 긴 오버행 면은 **층마다 점이 하나씩 쌓인다.**
> 층높이 0.05mm 기준 12mm 높이면 최대 240층 → 같은 자리에 최대 240점.

서포트 탭(레거시)은 모델 전체에 4mm 격자를 **한 장** 깔기 때문에 애초에 수십 개를 넘지 않는다.

---

## 2. 두 경로 비교

| | **서포트 탭 (레거시)** | **재설계 (S-4b)** |
|---|---|---|
| 진입 | "자동 서포트" 버튼 | "서포트 생성(재설계)" 버튼 |
| 검출 | 모델 전체 **4mm 격자** + 면 법선 각도 | **2D 층 그래프** (0.05mm 층마다 슬라이스) |
| 판정 | `normal·(-Y)` 가 임계각 이내 | 아래층과 겹침 + 층-팽창 r=lh/tanθ |
| 점 위치 | 격자 교차점이 **우연히** 걸린 곳 | 검출 영역에서 **직접** 샘플링 |
| 개수 | 수십 개 | 수백~수천 개 |
| 파일 | `support/utils/auto-generate.ts` | `support/detect/layer-graph.ts` + `place-points.ts` |

**설계 의도상 재설계가 더 많은 건 정상이다.** 레거시는 "작은 아일랜드에 서포트가 아예 안 붙는" 치명적 결함이 있었고(진단_아일랜드서포트_20260715), 재설계는 그걸 고치려고 "받칠 곳을 직접 찾아 반드시 점을 찍는" 방식으로 바꿨다. 문제는 **필요 이상으로** 많다는 것.

## 3. 주범 — 층별 중복 제거 (핵심)

`support/detect/place-points.ts` 의 `overhangContacts`:

```ts
function overhangContacts(overhang: OverhangRegion, params): Point2[] {
  const step = Math.max(params.overhangSpacingMm, 1e-3);   // 3mm
  const seen = new Set<string>();
  for (const [x, z] of overhang.points) {
    const key = `${Math.round(x/step)},${Math.round(z/step)}`;
    if (seen.has(key)) continue;                            // ← seen 이 이 함수 안에서만 산다
    ...
  }
}
```

`seen` 이 **함수 지역 변수**이고, 이 함수는 `OverhangRegion` **하나(=층 하나)** 마다 호출된다
(`placeSupportPoints` 의 `for (const overhang of detect.overhangs)`).

→ 3mm 격자 중복 제거가 **XZ 평면에서만, 그것도 같은 층 안에서만** 동작한다.
→ 같은 XZ 좌표라도 **층이 다르면 별개 점**으로 살아남는다.

### 수치

| 오버행이 걸린 층 수 | 층당 점 | 최종 점 수 |
|---|---|---|
| 10 | 1 | 10 |
| 50 | 3 | 150 |
| 200 | 3 | **600** |

12mm 높이 모델 = 240층(층높이 0.05mm). 경사면이 세로로 길수록 폭발한다.
리드가 본 "1,000+"가 정확히 이 형태다.

### 왜 후단 중복 제거로도 안 걸러지나

`preprocess-points.ts` 의 `dedupeSupportPoints` 가 3D 거리로 한 번 더 거르지만
기본값이 **`DEFAULT_DEDUPE_MIN_DIST_MM = 0.1`** 이다.
층 간격이 0.05mm 이므로, 같은 XZ 에 수직으로 쌓인 점들은 **0.1mm 마다 하나씩 살아남는다**.
12mm 기둥이면 120점. 줄기는 하지만 근본 해결이 아니다.

## 4. 두 번째 요인 — 지지반경 곡선 미구현

설계 3-2 는 "z 높이가 높을수록 지지 반경이 커진다(= 점이 성겨진다)"는 경험 곡선을 쓰기로 했다.

| z (mm) | 지지 반경 (mm) |
|---|---|
| 0 | 3.2 |
| 3.9 | 4.0 |
| 15 | 5.0 |
| 40 | 6.0 |

현재는 `fillSpacingMm` / `overhangSpacingMm` **고정 3.0mm** 이고 코드에 `TODO(설계 3-2)` 로 남아 있다.
높은 곳도 낮은 곳과 똑같이 촘촘하게 찍힌다.

## 5. 세 번째 요인 — 기둥 공유는 "기둥"만 줄인다

`clusterForSharedPillars`(S-4b-2b)가 121점 → 28기둥으로 76.9% 줄인 실측이 있지만,
이건 **기둥 수**를 줄이는 것이지 **접점(모델에 닿는 자국) 수**를 줄이지 않는다.
리드가 화면에서 "많다"고 느끼는 것은 접점과 다리를 포함한 전체 구조물이다.

우하단 통계 패널(C-4)의 `접점` 과 `기둥` 을 나눠 보면 이 구분이 바로 보인다.

## 6. 수정 방향 (후속 과제 — 아직 적용 안 함)

우선순위 순. **①만으로도 대부분 해결될 것으로 본다.**

### ① 전역 3D 중복 제거로 전환 (가장 효과 큼, 가장 안전)
`overhangContacts` 의 `seen` 을 **점 생성 전체에 걸친 하나의 Set** 으로 올리고,
키를 XZ 2D 가 아니라 **XZ + Y 를 함께** 양자화한 3D 격자로 바꾼다.
- 수직으로 쌓인 중복이 사라진다.
- 검출(`layer-graph.ts`) 은 **손대지 않는다** — S-4b-2e 검수분 보존.
- 점 생성만 바뀌므로 헤드리스 검증이 쉽다.

### ② 지지반경 곡선 적용 (설계 3-2, 기존 TODO)
`overhangSpacingMm` 고정값 → `z` 의 함수로. 높은 곳이 성겨진다.

### ③ 사용자 조절 UI 노출
현재 `overhangSpacingMm` / `fillSpacingMm` / `smallAreaMm2` 는 **슬라이더가 없다**
(`SUPPORT_DETECT_PARAM_LIMITS` 에 한계값만 선언돼 있고 UI 가 안 읽음).
리드가 "너무 많다" 고 느낄 때 직접 줄일 수 있어야 한다. → S-4d 범위지만 앞당길 가치 있음.

### ④ 레거시 경로 정리 시점 재검토
두 버튼이 공존해 혼란을 준다(로드맵 B-16 "언제 통합할꺼야?" 와 같은 맥락).
재설계가 안정되면 레거시 자동 서포트는 폐기 — disc 폐기(S-4a-2)와 같은 방식.

---

## 7. 즉시 확인 방법

수정 전이라도 리드가 지금 버전에서 확인할 수 있는 것:

- **우하단 통계 패널**에서 `전체` vs `기둥` 을 비교 → 기둥 공유가 실제로 얼마나 줄였는지
- **오버행 각도를 올리면** 점이 준다(45°→60°). 각도 게이팅은 정상 동작 중(S-4b-2e).
- 다만 **간격(spacing)은 UI 로 못 바꾼다** — ③번 과제.
