## 0. 한 줄 결론

**문서의 대표 권고(서포트 트리·Fork·3단 폴백·충돌 회피·공간 인덱스·부품 조립·순수 모듈)는 이미 우리 코드에 구현돼 있고, 일부는 문서보다 더 정교하다.** 그래서 "문서대로 갈아엎기"는 기각한다.
진짜 빈 곳은 **4가지**뿐이며 그것만 적용한다.

> ⚠️ **문서를 그대로 따르면 안 되는 이유(중요)**: 세 문서 모두 **CHITUBOX 바이너리 정적 분석** 산물이다. 우리 프로젝트의 확정 전제는 `docs/설계_서포트재설계_20260720.md` 전제③ — **PrusaSlicer 개념 기반 클린룸**이다. 두 문서군은 결론이 대체로 수렴하므로(트리·폴백·공간분할) 개념 채택에 충돌은 없다. 다만 **CHITUBOX의 내부 상수·클래스 구조를 "정답"으로 삼아 우리 구조를 갈아엎는 것은 근거가 약하다** — 문서 스스로 Density 공식·각도 임계식·샘플링 분포·트리 코스트를 전부 "미확정"으로 표기한다.

### 특히 "GPU Color-ID Picking" (view94 9장) — **기각**

문서의 핵심 권고 중 하나지만 우리에겐 **불필요하고 위험하다**.

- **불필요**: CHITUBOX는 Qt/직접 OpenGL이라 픽킹을 직접 만들어야 한다. 우리는 Babylon 위에 있고, 실제 병목이었던 곳(서포트 라우팅 광선)은 이미 `triangle-index.ts` 로 해결했다(288ms). 상호작용 픽킹(클릭 1회/브러쉬 이동)은 현재 체감 문제가 보고된 적이 없다.
- **위험**: RGBA8 ID 버퍼는 문서 스스로 경고하듯 MSAA/sRGB/blending을 전부 꺼야 하고, Babylon의 렌더 파이프라인·HighlightLayer·renderingGroup 과 충돌한다. `scene-refs.ts` 45 refs + 34-메서드 핸들 위에 별도 렌더 패스를 얹는 비용이 이득을 압도한다.
- **결론**: 픽킹 성능이 실제로 문제가 되면(대형 모델 브러쉬), 그때 **기존 `triangle-index` 를 상호작용 픽킹에도 재사용**하는 편이 훨씬 싸다. GPU 픽킹은 채택하지 않는다.

### "CPU MeshData / BVH / adjacency 전면 도입" (view94 3장) — **부분 기각**

- BVH는 이미 `triangle-index.ts` 헤더가 균일격자를 고른 이유를 명시했고 실측으로 뒷받침된다. **교체 근거 없음.**
- 다만 `extractWorldTriangles` 가 호출마다 전체 재할당하는 것은 실제 낭비다 → §3-B 후속 과제로 등재(이번 범위 밖).

## 2. 채택 — 이번에 적용하는 4건

### C-1. 커서 기준 줌 (view94 7.3/7.4) — **채택, 최우선**

- **문서 근거**: view94 7.3/7.4 + Acceptance Test "확대 후 그 점이 화면에서 크게 벗어나지 않음". 문서가 "적극 채용 권장"이라고 명시한 유일한 항목.
- **우리 현황**: `useSceneBootstrap.ts` 가 `zoomToMouseLocation` 을 설정하지 않음 → Babylon 기본 `false` → 화면 중앙 기준 줌.
- **핵심**: 이건 신규 기능이 아니라 **v1 회귀**다. 구 v1 `utils/babylon.utils.ts:75-79` 는 `zoomToMouseLocation = true` 를 명시적으로 켜 두었고, v2 이관 때 누락됐다.
- **판정**: 명백히 좋다. Babylon이 이미 지원하므로 비용도 1줄. **B-19(줌 확대 한계 걸림, 리드 관찰 요청) 의 유력한 원인이기도 하다** — 중앙 기준 줌은 모델 가장자리를 볼 때 `lowerRadiusLimit` 에 먼저 걸린다.

### C-2. 출력영역 초과 경고 표시 (view94 15장) — **채택**

- **문서 근거**: view94 15장 + Acceptance Test "모델을 Plate 밖으로 옮기면 해당 부분이 경고색".
- **우리 현황**: **전무.** 플레이트 밖으로 나가도 아무 표시가 없다. `plateWidthMm/plateDepthMm` 는 격자·카메라·래스터화에만 쓰인다.
- **판정**: 실사용 가치가 명확하다. 슬라이스하면 잘려 나가는데 그 전에 알 수 없는 것은 실질적 결함이다.
- **단, 문서의 Shader 방식은 기각**: 우리는 `StandardMaterial` 기반이고 커스텀 셰이더를 도입하면 오버행 vertex-color 와 충돌한다. **CPU AABB 검사 + 외곽선/배지 경고**로 간다(문서도 15장 말미에 "최종 판정은 별도 CPU AABB 검사로도 수행"이라고 인정).

### C-3. 검출각 단일화 (view94 14장 / supp94 16장) — **채택**

- **문서 근거**: 두 문서가 **가장 강하게 반복**하는 원칙. view94 14장 "Auto Support가 사용하는 Overhang threshold와 Viewer의 hangZ 계산을 같은 utility 함수로 통일한다 … 이렇게 해야 화면 표시와 실제 Auto Support 결과가 어긋나지 않는다". supp94 16장도 동일.
- **우리 현황**: **정확히 이 함정에 빠져 있다.**
  - 뷰어 빨간 하이라이트: `SupportParams.overhangAngleDeg` = **45°** (`utils/overhang.ts`)
  - 실제 서포트 검출: `LayerGraphParams.overhangAngleDeg` = **30°** (`DEFAULT_LAYER_GRAPH_PARAMS`)
  - 게다가 **판정 방식도 다르다**(전자는 면 법선, 후자는 층-팽창 r=lh/tanθ).
  - UI 슬라이더는 45° 쪽에만 달려 있다 → **사용자가 슬라이더를 움직여도 실제 서포트 검출은 안 바뀐다.**
- **판정**: 문서 지적이 정확하고, 우리 실물 혼란의 원인이다. 화면의 빨간 면과 실제 점이 찍히는 곳이 다르면 사용자는 도구를 신뢰할 수 없다.
- **적용 범위(보수적)**: **검출 알고리즘은 건드리지 않는다**(S-4b-2e가 방금 검수 통과했다). 하이라이트가 검출과 **같은 각도값**을 쓰게 하고, UI에 검출각 슬라이더를 노출한다. 판정식 통일(층-팽창 ↔ 법선)은 후속 과제로 등재.

### C-4. 서포트 통계 (supp94 46장) — **채택**

- **문서 근거**: supp94 46장 — EXE에 `total Support Num:` / `Up Touch Support Num:` / `Main Support Num:` 문자열 확정 존재. "CHITUBOX 결과와 비교하는 역검증에도 매우 유용하다".
- **우리 현황**: `RouteReport` 10개 카운터가 이미 계산되지만 **`console.log` 로 흘려버린다.** UI에 없다.
- **판정**: 이미 계산 중인 값을 화면에 띄우는 것뿐이라 비용이 거의 0인데, 가치는 크다. 리드가 실물 테스트마다 확인하는 값(점 수, 기둥 수, 실패 수)이 바로 이것이고, **로드맵의 "상용은 20개 미만인데 우리는 1,000+" 같은 대조를 매번 콘솔 열어서 하고 있다.**

## 3. 채택하되 이번 범위 밖 — 후속 등재

### A. Worker화 + 취소 (supp94 11장) — **개념 채택, 별건**

문서 지적은 옳다(현재 서포트 생성 전 과정이 메인스레드 동기, 진행률·취소 없음). 다만 이는 **S-2(성능 편입)로 이미 등재된 기존 과제**이고, 검출·라우팅 전체를 워커로 옮기는 것은 이번 학습 적용과 별개의 대형 작업이다. 로드맵 S-2에 CHITUBOX 근거를 보강 기록.

### B. `extractWorldTriangles` 캐싱 — **별건**

호출마다 전체 재할당 + 생성 1회에 2번 호출 + 인덱스 매번 재구축. 문서 30장 "Camera 이동 때문에 VBO를 재생성하지 않는다"의 정신과 통한다. 성능 과제로 등재.

### C. Coverage/Supplement 패스 (supp94 32~34장) — **개념 채택, 후속**

"1차 결과를 다시 검사해 지원이 부족한 영역을 찾는 후처리". 우리는 전무하며(실패 점은 그냥 버려짐), 문서 지적대로 이는 품질에 직결된다. **다만 S-4c/S-4d 이후가 맞다** — 바닥판·수동 편집이 없는 상태에서 보완 패스만 넣으면 검증할 기준이 없다. 로드맵에 신규 항목으로 등재.

### D. 지지반경 곡선 (설계 3-2, 이미 우리 TODO) — **후속**

supp94 0.2 "Density ↑ → spacing ↓" 실사용 검증과, 우리 설계서 3-2 z높이별 곡선이 같은 이야기다. 현재 `fillSpacingMm`/`overhangSpacingMm` 고정값 + 명시적 TODO. 등재 유지.

### E. 수동 서포트 = 같은 Tree Builder 재사용 (supp94 28장) — **후속(S-4d)**

문서의 "나쁜 설계: Manual/Auto 엔진 2개" 경고가 우리에게 정확히 해당한다(레거시 manual = Lathe, 재설계 = 조립). 이미 S-4d 범위이며 `kind:'manual'` 자리도 타입에 예약돼 있다.

## 5. 라이선스·출처 메모

- 세 문서는 CHITUBOX 바이너리의 **관찰된 동작** 기술이며, 원본 코드가 아니다. 이번 적용분(C-1~C-4)은 어느 것도 CHITUBOX 코드 구조를 이식하지 않는다:
  - C-1 = Babylon 내장 플래그 1줄(+v1 회귀 복구)
  - C-2 = 자체 AABB 비교
  - C-3 = **우리 파라미터 2개를 하나로 잇는 배선**
  - C-4 = 이미 우리가 계산 중인 카운터의 표면화
- 프로젝트 정본 전제(설계서 전제③ PrusaSlicer 클린룸)는 그대로 유지된다. 이번 문서는 **교차 검증 자료**로 쓰였다 — 두 출처가 독립적으로 같은 구조(트리·폴백·공간분할)에 수렴한다는 사실이 우리 현행 설계의 타당성을 오히려 강화한다.

## 6. 학습으로 확인된 것 (적용은 없지만 기록 가치)

1. **우리 3단 폴백 순서가 CHITUBOX와 일치한다.** supp94 26장의 회피 흐름(Use → alternate trunk → offset/turn → new trunk)이 우리 0/1/2/3단과 같은 형태다. 독립 출처의 수렴 = 설계 타당성 방증.
