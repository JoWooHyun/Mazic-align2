## 0. 한 장 요약

1. **"저쪽이 더 좋아 보이는" 이유의 대부분은 웹 한계가 아니라 우리 설정값이다.** 프루사 렌더러가 요구하는 GPU 기능은 WebGL2(우리 Babylon 6 이 쓰는 것)로 전부 된다.
   차이를 만드는 건 ① **고해상도 화면 미대응**(배율 125~150 % 노트북에서 화면을 낮은 해상도로 그린 뒤 늘림 → 흐릿함) ② **조명이 월드에 고정**(밑면·뒷면이 어둡고, 면의 굴곡이 잘 안 보임 — 프루사는 조명이 카메라에 붙어 어느 각도에서 봐도 같은 밝기) ③ **광택 거의 0**(면 경계가 덜 읽힘) ④ **1 px 선**(격자·외곽선·축·단면선이 가늘고 계단짐) ⑤ **호버 반응 없음·바닥판이 반투명 회색판** — 다섯 가지다. 전부 화면 전용 수정이라 **출력 파일 바이트는 안 바뀐다.**
2. 기능 격차 중 큰 것은 **슬라이스 후 3D 미리보기**다. 프루사·오르카는 "전 층을 3D 로 쌓아 보여 주고 층 범위(위·아래 손잡이 2개)·층 안 진행을 슬라이더로 자른다". 우리는 3D 는 메쉬를 평면으로 자른 단면 1장, 경로는 2D 패널에 층 하나씩이다. 웹에서도 충분히 만들 수 있다(브라우저 슬라이서·G-code 뷰어가 이미 한다).
3. **웹이라 정말 어려운 것**은 몇 개 안 된다: 3D 마우스(SpaceMouse), 운영체제 파일 연결(`.gcode` 더블클릭으로 열기), 탭 메모리 한도(수천만 선분급), 브라우저 단축키 충돌(Ctrl+휠 = 브라우저 확대 등 — 대부분 우회 가능). 우리 대상(치과 STL 수십 MB·Task0 수백 층)에선 메모리도 문제 안 된다.
4. 추천: **데모 전 "화질 묶음"(§5-A, 하루 안팎, 산출물 무관)** → 데모 후 3D 경로 미리보기·편집 화면 단면 보기·층 범위 슬라이더(§5-B). 직교 투영은 "축 방향 뷰 버튼을 누를 때만 직교" (오르카 2.3 방식)로 다시 제안 — ★ 리드 결정.

## 3. 웹이라서 — 할 수 있는 것 / 어려운 것 / 웹이 나은 것

### 3-1. 웹에서도 똑같이 되는 것 (= 차이는 우리 구현 몫)

- **렌더링 품질 전부**: 고해상도·MSAA·방향광·광택·텍스처·외곽선·SSAO·그림자·직교 투영. WebGL2 는 OpenGL ES 3.0 급이고, 프루사·오르카 뷰어가 쓰는 기능(정점·조각 셰이더, 인스턴싱, 다중 샘플)은 그 안에 다 있다. Babylon 6 은 SSAO·그림자·GreasedLine·WebGPU 엔진까지 갖고 있다.

- **우클릭 메뉴·단축키 대부분**: 이미 함(`뷰어조작체계.md`).

## 5-1. 좌표계 비교 (10/29 추가 — 리드 질문 "그 좌표계는 어때?")

### 용어 정리 (리드 10/29 관찰 반영)

프루사·뱀부·오르카의 좌표 선택 상자는 두 가지 중 하나를 고르게 한다. 번역마다 이름이 다를 뿐 뜻은 같다.

| 프로그램 표기 | 뜻 | 새로 불러온 모델의 위치 숫자 | 회전·크기 |
|---|---|---|---|
| **월드 / 영역 / 절대 좌표** | 베드(판)에 붙은 자. G-code 숫자와 같은 계열 | **판 가운데 좌표**(예: 판 256 mm 면 X 128·Y 128, Z = 높이 절반) | 축이 판에 고정 — 모델을 돌리면 X·Y·Z 크기가 달라짐 |
| **객체 좌표** | 모델 자신에 붙은 자. 원점 = 모델 자기 중심 | **0, 0, 0** | 축이 모델과 같이 돎 — 돌려도 크기 일정, 이동도 모델의 기울어진 축 방향 |

**우리 패널은 월드 좌표 하나뿐인데, 원점이 판 가운데 근처라** 새 모델이 X 0·Y 0·Z(높이 절반)으로 보인다 — 숫자는 객체 좌표처럼 보이지만 축은 판에 고정된 월드 좌표다. 그래서 "월드 좌표인데 0 근처" 라는 두 프로그램 어디에도 없는 모양이 됐다.
또 새 모델은 world 원점(베드 75, 42.5)에 놓이는데 화면 판(출력 가능 영역) 가운데는 베드 (80, 47.5) 라서, **새 모델이 판 가운데에서 앞-왼쪽으로 5 mm 비켜 놓인다.**

### 결론

**축 방향·회전 방향은 프루사·오르카와 같다(10/15 #142 로 맞춤). 다른 것은 "숫자의 원점"과 "불러올 때 원래 위치를 버리는 것"이다.**
출력 파일(run.gcode·PNG)은 `task0-frame` 한 곳에서 베드 좌표로 바꿔 쓰므로 맞다 — 아래 차이는 전부 **화면 숫자·배치** 문제다.

## 6. 불확실·미확인 (추측으로 구현하지 말 것)

- 오르카의 선택 **외곽선** 렌더링 유무 — 문서 근거를 못 찾았다(검색에 나온 외곽선 설명은 Lychee 문서).
- 프루사 SLA 미리보기가 층 단면을 정확히 어떤 색·방식으로 그리는지 — 확인한 것은 "자르기 평면은 카메라와 평행, Ctrl+휠로 이동"(1.42 beta2 노트)과 "층 면적·시간 창"(2.7.5) 뿐.
- 프루사 2.8 새 G-code 뷰어가 OpenGL ES(=WebGL 과 같은 계열) 경로를 공식 지원하는지 — 소스에 `src/libvgcode` 폴더는 있으나 ES 지원 여부는 확인 못 함. 결론(§3-1 "웹으로 같은 품질 가능")은 이것과 무관하게 성립한다.
- A1 의 실제 효과 — 리드 PC 배율에 달림(§5-C).
- 프루사 위치 Z 가 "바운딩박스 중심" 이라는 것 — 포럼 답변 기준(2019), 현행판 실행 확인 안 함. "다재료 프린터에서 여러 파일 → 다파트 물체로?" 질문 문구도 기억 기반 — K4 설계 전에 프루사로 직접 확인.
